## 2. P1-2 `原文/` 目录是发布链旁路，下次重建会静默删除 777 个文件

**事实链**

1. `工程/题库调研/build_dist.mjs:21-29` 白名单 `FILES`（11 个文件）+ `DIRS = ['data']` —— **不含 `原文/`**。
2. `site_dist/` 顶层实测：`["app.js","data/","english.js","favicon.svg","features.js","index.html","lixiangguo.html","manifest.webmanifest","styles.css","sw.js","sync.js","themes.css","原文/"]` —— **`原文/` 在发布目录里，但不在白名单里**。
3. `site/原文` = **777 文件 / 3.43MB**，`site_dist/原文` = **777 文件**（大小一致）→ 是手工复制过去的。
4. `site/lixiangguo.html:300`：`<a class="hero-cta" href="原文/理想国_郭斌和张竹明译本.html">开始阅读 →</a>` —— **硬依赖该目录**。

**触发路径（高危）**：任何人现在跑一次

```
node 工程/题库调研/build_dist.mjs
```

脚本第 61 行 `fs.rmSync(DIST, { recursive: true, force: true })` 先清空 `site_dist/`，随后只复制白名单 + `data/` → **`原文/`（777 文件）整体消失**；而第 68 行的 `unexpected` 检查只扫**重建后**的顶层，此时 `原文/` 已不存在，**不会报 FAIL** → 静默丢失，用户点"开始阅读"直接 404。

**顺带**：这也解释了口径混乱 —— `原文/` 从未经过泄漏扫描（`leaks`），因为扫描只覆盖白名单产物。

## 3. P1-3 A02「统一 id 网」实际落地规模是声称的 1/6，且用户进度死链被 WARN 掩盖

### 3.1 声明 vs 实测

### 3.2 硬证据

```

```

- **站点分片确实带别名**（`build_site_data.mjs:276` `if (q.flags) o.f = q.flags` 透传），但总数就是 383 条。
- verify 自身输出：`⚠ lpc 题目引用 149/419 = 35.56%（未解析 270 条 {"ext-hash":270}）`；`主 id 14885 / 别名 386`（= 383 + 3 orphan，自洽）。
- 我另取快照 `database_export-…-progress.json` 独立复算：**lpc 的 270 个 `ext-` 引用，在全库 108,023 个主 id + 1,713 条别名中命中 0 条**。

### 3.3 两处必须纠正的解读

1. **lql 的「3,104/3,104 = 100%」不能证明别名网有效**。lql 的 3,104 个引用里 **`ext-` 数量 = 0**（3,095 命中分片主 id + 6 条 AI 变式兜底 + 3 条 orphan 兜底 = 3,104 ✓ 完全自洽）。他从未刷过扩展题，**根本没用到别名网**。
2. **「lpc 未解析均为未上线学科的历史标记」与明细自相矛盾**。WARN 明细指向 `session r:bio`、`session c:bio:x第一章 蛋白质的结构与功能` —— **bio 是已上线学科**。这条解释站不住。

### 3.4 未确证项（诚实标注）

本轮**未能确证**这 270 条是"可救"还是"永久丢失"。旧扩展 id 规则为 `ext-<sha1(dupKey).slice(0,16)>`（`build_packs.mjs:147,313`），反推需 `merged2` 的 `dupKey` 全集重算哈希。**建议的排查路径**：对 bio/physiology/immunology 的 merged2 题批量算 `"ext-"+sha1(dupKey).slice(0,16)`，与这 270 个 hash 求交集 —— 命中即"题还在库里、只是 id 漂移"，可用按 dupKey 重建别名的方式救回；全不命中即确认为历史快照残留。

### 3.5 补验结论（2026-09-13 晚，已推翻了 3.4 的"未确证"）

**口径修正**：本节 3.2 所用的用户快照若取自 `E:\_shuatiji_outside\userdata_export\`（mtime 08-31）则 lpc 无 `ext-` 引用。**正确快照 = 工作区根 `database_export-shuatiji-d9gm0j668e9396859-progress.json`（mtime 09-13 03:16）**，即 `verify_id_zeroloss.mjs` 的 `findSnapshot()` 实际命中那份：lpc `subjects=[bio]`、题引用 419、主体数组 `ext-` **0**、session `ext-` **275（去重 270）**。

**270 条确认可救，且根因已定位**：

| 验证 | 结果 |
|---|---|
| lpc 死链 id ↔ 历史 packs id | `ext-32dbc01223f22470` **精确等于** `bak_packs_20260913/.../bio-ext.json` 第 0 条 |
| 历史基线（A02 前）bio 扩展题主 id | **全 `ext-<sha1>` × 3,162** |
| 当前站内 bio 扩展题 | **3,162 条一条没少，主 id 全换成 srcid** |
| 用历史基线作 PREV 反查 | **hit 3162 / miss 0 / ambig 0** |
| lpc 270 条可恢复 | **270 / 270 = 100%** |

**根因**：`build_packs.mjs` 扩展组别名候选只有 `sourceDetail 来源 id` + `prevId（上一版主 id）`；A02 那次构建的基线（`工程/题库调研/packs`）里扩展题主 id 已是 srcid → `prevId === primaryExt` → 旧 `ext-` 从未进候选。叠加**设计缺陷**：扩展组构建时**不继承上一版 `aliasIds`** → 跨 ≥2 次 id 变更即永久丢失。

**修复**：① 改 `build_packs.mjs` 扩展组继承 `prevAlias`（防复发）；② 用 `E:/_shuatiji_outside/bak_packs_20260913/packs` 作 PREV 重建一次（恢复，预期 aliasIds 1,713 → ~66,000）。代价：三科扩展题 9,980 条 × 41B ≈ +400KB raw / ~+130KB gz，分片懒加载、首屏零影响。

详见专项报告 `A02_别名网根因与修复_20260913.md`。
