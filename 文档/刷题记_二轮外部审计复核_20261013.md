## 二、P0-2 复核细节：审计漏看的兜底链

审计场景推演到"刷新后 `dirty=false`，Q1 永不回传"就停了。实际链路：

1. `reconcile()` L344 置 `dirty=true` 后，L348 `setTimeout(location.reload, 350)`；
2. **`location.reload()` 会触发 `beforeunload` → `sync.js` L439 绑定的 `forceFlush()`**；
3. `forceFlush` L367-390 读 LS（此刻已是合并结果）→ `sendBeacon` 推送（token 在 body，服务端 L459-464 接受 `payload.token`；CORS 预检 OPTIONS 在服务端 L441 有 204 应答，beacon 可通过）。

所以**常见路径下合并结果在刷新瞬间已经推上云端**，第三台设备能看到 Q1+Q2。审计建议的六个回归测试中"合并后刷新"一条大概率会通过。

**但残余缺口真实存在**：beacon 静默失败（弱网/浏览器丢弃）时，刷新后 `dirty=false`、且无人再补推。而恢复信号其实已经持久化了——`meta.local > meta.cloud`（L342 只更新了 `m.local` 没动 `m.cloud`），只是没有任何代码消费它。

**低成本修法（不必上持久化 dirty 对象）**：`validateAndEnter()` / `reconcile()` 开头加一句——`if (meta().local > meta().cloud + 1000) dirty = true;`。一行兜底 + 六个回归测试照跑。

## 三、对 P0-1 的整改立场（与审计建议的差异）

审计要求一步到位 revision+CAS（baseRevision+冲突重试）。**我认为对该项目规模，第一步做 5 行的"服务端 updatedAt 单调闸"性价比更高**：

```js
// push() 内，set 之前：
const cur = await db.collection(COL.progress).where({ _id: t.uid }).get();
const prev = cur.data && cur.data[0];
if (prev && prev.updatedAt && updatedAt && updatedAt < prev.updatedAt)
  return { ok: false, msg: "本地版本较旧，已跳过（将以下次同步合并）", stale: true };
```

- **消灭的正是最常见故障**：乱序到达（旧请求后完成）覆盖新数据——审计风险示意图里的主场景；
- 不能消灭的只剩"两请求同时通过检查"的窄窗口（毫秒级），对单用户多设备场景概率可忽略；
- CAS 协议需要客户端全链路改 baseRevision，复杂度高，留作真有多设备高频并发需求再做。

审计说"不要简单加先查再 set"在分布式严格性上正确，但没给出与项目规模匹配的分级方案。

## 五、审计未提及但复核中发现的补充点
