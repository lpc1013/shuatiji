## 方法与边界

执行 `node 工程/题库调研/verify/run_all.mjs --full`，并独立读取全部生化解析分片，与 packs 输入、当前题目主 ID 比对。另通过 Node VM 注入复制失败、目录读取失败、嵌套文件和版本错配，用 jsdom 注入永不完成的题包请求。故障注入使用内存文件系统，不触碰生产目录。

范围包含构建可靠性、产物一致性、发布准入、缓存更新和启动可用性。未做线上请求、云端权限或并发写入测试，也未完成真实浏览器的移动端视觉、无障碍、性能与 Service Worker 生命周期验收。本报告不据此判断线上部署版本是否与本地一致。

## F01 · 生化解析未完整进入站点

**证据：** `verify_schema_unified.mjs:178` 的计数断言失败，完整套件返回 1。独立比对结果如下：

| 指标 | 结果 |
|---|---:|
| packs 生化解析条目 | 5,682 |
| site 生化解析条目／唯一 ID | 5,071／5,071 |
| packs 有、site 无 | 611 |
| 缺失且主 ID 属于当前站点题目 | 543 |
| site 独有解析／重复 ID | 0／0 |
| 共有条目的内容差异 | 0 |

缺失的当前题目示例：`ext-7c7fb70dc5a10892`、`ext-0af2355189c0d574`、`ext-d119bb1c61fce76d`。因此这不是仅由“输入包含未上线题目”造成的计数误报。`site/` 与 `site_dist/` 的现有一致性检查通过，说明发布副本与这个缺失状态一致。

**影响：** 对上述 543 道题，当前静态解析映射没有对应条目；刷新或重试下载无法补回产物本身没有的数据。这里确认的是输入已有解析未进入站点，不是判定这批解析的医学内容正确。

**建议：** 在临时输出目录重建，先定位章节归属、过滤条件或产物更新环节，再对缺失 ID 做集合核对。对有意排除的输入显式登记原因，不应通过降低计数断言来消除失败。

**验收：** 当前题目应具备的解析全部可按主 ID 找到；全量内容比较通过；`--full` 返回 0。

## F02 · 打包错误没有变成失败状态

**位置：** `deploy.mjs:37、52、94、127、141`。

复制失败虽累计到 `fail`，但 full、inc 两种模式都没有据此设置非零退出码。目录读取异常仅记录日志后继续，甚至未计入 `fail`。full 模式还忽略 `safeRmSync(DIST)` 的返回值。

**复现：** 对真实 `deploy.mjs` 执行逻辑替换文件系统依赖：令 `app.js` 所有复制尝试抛出 EACCES，full 模式仍输出“OK site_dist 就绪”，inc 模式输出 `failed:1` 后正常返回。令源 `data/` 读取抛出 EACCES，full 模式也正常返回。模拟用于验证错误传播，不是完整的真实磁盘产物验证。

**影响：** 单独调用打包入口的上层自动化可能把缺失文件或未更新资源当作成功产物。`release.mjs` 后续的完整校验可捕获部分问题，这是已有缓解，但直接上传路径没有该保障，见 F03。

**建议／验收：** 删除、枚举、复制、清理任一必需操作失败即中止并非零退出；输出先写临时目录，完整校验成功后再替换发布目录。分别注入这些故障，确认旧产物保留且上传步骤未执行。

## F03 · 上传入口没有强制发布验收

**位置：** `deploy_edgeone.mjs:34–72`；对照 `release.mjs` 的步骤编排。

上传脚本仅检查 `site_dist/` 是否存在，随后复制文件、生成绑定配置并启动 CLI。它没有调用 `release.mjs`、`run_all --full`、严格产物扫描，也没有验证与当前产物哈希绑定的验收记录。

**复现条件：** 保留当前目录，直接运行上传入口即可到达上传控制流，即使此前完整校验失败。为避免实际发布，本次仅检查控制流，没有执行上传命令。

**影响：** F01 这种已被测试识别的失败，并不能由代码层面阻止直接上传；旧产物或手工污染的产物也可能被选用。

**建议／验收：** 让发布入口负责“构建→校验→上传”，或让上传入口验证同一产物的哈希与验收记录。修改任一已验收文件、制造 F01 或 F02 后，确认 CLI 子进程均不会启动。

## F04 · 白名单只限定顶层目录，未限定目录内可发布内容

**位置：** `_whitelist.mjs:18、22`；`deploy.mjs:56、117`。

`data/`、`原文/` 允许递归复制，`DENY_ANY` 仅匹配少量备份和压缩文件名称。它不匹配 `.env`、`credentials.json`、`private.key` 等。把模拟 `.env` 放入 `data/` 后，实际复制逻辑接受了该文件；同一黑名单用于后置扫描，也无法据此拒绝它。

**前提与影响：** 必须先有人或工具把敏感文件放入获准目录，才会形成泄漏。**本次没有确认现有产物含真实秘密，也未确认托管平台是否对这类文件另有阻拦。** 风险是打包器所声称的泄漏扫描无法提供这层保障。

**建议／验收：** 用生成清单限定允许发布的文件路径及类型，拒绝非预期隐藏文件和凭证文件；必要时增加内容检测。分别注入上述文件到两类目录，确认构建拒绝，且正常 JSON 与阅读资源可发布。

## F05 · 版本查询参数没有保证发布内容不可变

**位置：** `app.js:118、281`；`sw.js:39–49`；`build_site_data.mjs` 的固定分片路径。

题包／解析沿用固定文件路径，仅附加 `?v=`。Service Worker 对任何带 `v` 的请求使用 cache-first；缓存未命中就请求服务器，并把响应存入该请求键。

**场景：** 旧页面持有 manifest A，发布 B 后才第一次打开某科或读取未缓存解析；若托管服务按常规静态文件方式对查询参数返回当前文件，`file.json?v=A` 实际取得 B 的字节。新 SW 激活清除旧缓存也会扩大旧页面的缓存未命中机会。

**复现：** 执行真实 SW fetch 处理器，模拟网络返回 B，向它发送 `a.json?v=release-A`，返回内容仍为 B。该测试证明客户端没有内容绑定校验；服务器是否保留历史版本未在线核实。

**影响：** 版本化 URL 不足以防止旧清单、新题包与新解析混用，可能造成计数、章节或答案解析不一致。

**建议／验收：** 采用内容哈希文件名或保留历史版本的发布目录，清单指向不可变资源；原子切换发布指针。让 A 页面跨越 B 发布后再加载未访问分片，必须得到完整 A，或明确提示刷新，不能静默取得 B。

## F06 · 分钟级版本号发生确定性碰撞

**位置：** `build_site_data.mjs:202`。

`new Date().toISOString().replace(/[-:T]/g, '').slice(0,12)` 只保留到分钟。`2026-10-15T01:02:01Z` 与 `01:02:59Z` 均生成 `202610150102`。若两次构建内容不同，SW cache-first 仍可复用第一次的缓存。

**建议／验收：** 从内容生成版本标识，并配合 F05 的不可变资源路径；同一分钟修改任一分片再构建，必须得到不同资源标识。单纯提高时间精度仍不能解决 F05。

## F07 · 悬挂题包请求阻断首屏和事件绑定

**位置：** `app.js:118–119、2654–2683`。

启动先等待清单、孤儿包和当前学科题包；题包请求没有应用级超时。`Promise.all` 要等待两个题包都结束，渲染及交互绑定发生在后面。现有失败重试可处理已 reject／非成功响应，不能处理一直 pending 的请求。

**复现：** 在 jsdom 中执行真实 `app.js`，清单与孤儿包正常返回，题包请求保持 pending。观察到两个请求在途、`#view` 为空、document 业务 click 处理器尚未绑定。观察窗口为 100ms；持续阻塞依据是未完成 Promise 的控制流，不是移动网络实测时长。

**建议／验收：** 尽早显示加载状态并绑定可恢复操作；给启动依赖设置超时和取消机制。分别使清单、孤儿包或单个题包悬挂，确认在明确期限内显示错误／重试入口，并能恢复。

## F08 · “零丢失”验收可以被静默降为未验证

**位置：** `verify_id_zeroloss.mjs:38`；`run_all.mjs` 的 full 步骤。

本次输出 `SKIP 未找到用户数据快照…`，该步骤返回 0。其余步骤通过时，编排器会把它计为成功，尽管没有验证真实用户快照的历史引用。

**影响：** 不证明进度已丢失，但“完整验收通过”不能据此解释成“已验证真实用户进度零丢失”。

**建议／验收：** 区分 PASS／FAIL／SKIP。日常开发可跳过；正式发布若要求零丢失，应强制提供经脱敏的代表性快照或等价固定回归样本。缺少样本时报告必须明确未验证，且不能满足该项发布要求。
