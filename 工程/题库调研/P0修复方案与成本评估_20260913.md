## A01 · 强制登录门禁 → 降级为可选（已确认 A1）

### 问题（当前代码实测）

| 位置 | 行为 |
|---|---|
| `sync.js:437-443` | `init()`：无 token → **直接 `showGate()`** |
| `sync.js:338-355` | `showGate()` → `#authGate` 全屏 + `body.gated{overflow:hidden}`（`styles.css:301-303`）锁死整页 |
| `sync.js:357-364` | `validateAndEnter()` **catch 吞掉网络错误**，统一走 `clearAuth()` + `showGate()` |

**最恶的一环**：`sync.js:361` 注释明写「网络错误 -> 回到门禁」。→ 断网 / 云函数抖动 / 手机切网，**都会清掉 token 并弹登录墙**，本地进度完好也进不去。

而 `app.js` 文案承诺「所有数据只存在这台设备的浏览器里」「纯本地个人学习站」—— 定位与行为直接矛盾。

### 改法（A1：降级为可选）

1. `init()`：无 token → `hideGate()`，正常进入；**门禁只在用户主动点顶栏账号按钮时出现**（`openAccount()` 已存在，直接复用）。
2. `validateAndEnter()` 拆分两条路径：
   - **服务端明确回 `未登录/过期`** → `clearAuth()` + 提示（不弹全屏，只 toast + 账号卡）
   - **网络异常 / 5xx / 超时** → **保留 token**、静默离线、进入学习；恢复后自动重试（复用已有 `failCount` 退避）
3. 文案统一：把「纯本地」改为「本地优先，可选云端同步」。

**验收**：断网打开 → 能正常刷题；云端下线 → 站点照常可用。

## A02 · 扩展题 id → 统一 id 网（已确认 B1，需扩展）

### 实测数据（merged2 全量 108,018 题）

| 指标 | 数值 |
|---|---|

| 带 iyixue 源 id | 80,680（74.7%） |
| **源 id 全局唯一数** | **82,290，重复 0** |
| 会被打成 `ext-<hash>` 的非极光题 | **65,010** |
| 其中带 iyixue 源 id | **64,991（99.97%）** |

### 报告漏掉的两点（本次发现）

**① 性质改判：不是"孤儿进度"，是"题库翻倍"。**

`build_packs.mjs:325-352` 有一层兜底：上一版 packs 有、本次未命中的题会**原位补回**（`flags.fromPrevPacks`）。所以题干一改的真实后果是：

- 旧 id 被补回（内容是**旧**题干）+ 新 id 新增（新题干）→ **站内同题出现两条**；
- 用户进度落在旧 id，刷到的却是新 id → 看起来"进度没记上"。

**推论**：只要以后调一次 `merge2` 的去重键规则或题干归一化规则，**65,010 题的 id 集体漂移 → 题库变 ~13 万条**。这不是"将来可能"，是"下次动 merge2 必然发生"。

**② 极光组只收 jiguang/oursite 的 id，iyixue 源 id 被丢弃 —— 这正是你说的"重复题已合并到极光"的坑。**

`build_packs.mjs:210-212`：

```js
const allIds = [...new Set((q.sourceDetail || [])
  .filter(d => d.id && (d.platform === "jiguang" || d.platform === "oursite"))   // ← iyixue 被排除
  .map(d => d.id))];
```

被合并进极光的重复题，其 iyixue 源 id **既不进主 id，也不进 `aliasIds`** → 彻底丢失。所以只改扩展组（B1 原方案）**不够**。

### 改法（统一 id 网 = B1 扩展版）

1. **收集全部来源 id**：`jiguang` / `oursite` / `iyixue`（+ 历史 `ext-<hash>`），不再过滤平台。
2. **主 id 优先级**：上一版 packs 正在用的 id → 极光/oursite → **iyixue 源 id** → `ext-<hash>` 兜底。
3. **所有非主 id 全部写进 `flags.aliasIds`**（含 iyixue 源 id）。
4. 网站侧 `ALIAS` 已能消费 → 任何来源 id 都能映射到主 id，**进度零丢失**。

**附带收益（回答你说的"按序排序"）**：源 id 形如 `ykb_201012_36101_800101`（年月_卷号_题号），**天然有序、可读、可定位**。对比现在的 `ext-3f2a9b7c...` 乱码，新 id 排障时一眼能看出是哪年哪卷哪题。

> ⚠️ 需你确认：「按序排序」你指的是 **(a) id 本身可读可排序**，还是 **(b) 站内题目列表按源 id 顺序展示**？两者做法不同，(b) 要额外定排序口径（源站顺序 / 年份 / 章节）。

**风险与验收**：改 id 规则会造成存量扩展题 id 漂移 → **必须**配套 `aliasIds` 回写。验收断言：`新 id 集合 ∪ aliasIds ⊇ 旧 id 集合`（我加进 `verify_packs`）。

### 实测数据

**后端**：CloudBase 云函数 `quiz`（`site/cloud/functions/quiz/index.js`）。`push` = 查一次 tokens + 写一次 `progress` 单文档；`pull` = 查 tokens + 读 progress。

### 真正的成本/风险点（不在频率）

1. **❗ localStorage 5 MB 上限才是硬顶**。state 已 436 KB，而 `sessions` 会随中断次数无上限累积。撞顶后 `save()` 会抛 `QuotaExceededError`，而 `app.js:346` 是 `catch(e){}` **静默吞掉**（审计 B07）→ **看起来在保存，其实没落盘**。这是最该修的。
2. **`pull` 吃外网出流量**（免费额度 1 GB/月）。单次 pull 下行 436 KB → 约 2,300 次/月用完额度。日常够用，但换设备/清缓存频繁时要留意。
3. **单文档 16 MB 上限**（CloudBase）→ 距上限还远，但不是无限。

### 改法（C1 实用版，成本极低）

| 部分 | 数据形态 | 合并策略 | 理由 |
|---|---|---|---|
| `wrong/fav/doubt/mastered` | 标记集合（数组） | **取并集** | 多端各自加标记是常态，并集零冲突；"取消标记"是极小概率 |
| `qstat/byChapter/daily` | 计数聚合 | 保留整块 LWW + 冲突提示 | 计数类无法简单相加（会重复计数），整块 LWW 影响面小 |
| `review` | 每题 map | 按题合并（`nextReview` 取更晚、`stage` 取更大） | 已有 per-question 结构，天然可合并 |
| `sessions` | 本机草稿 | **不同步** | 占 78% 体积，且"换设备续练"本就该是本地行为 |

**配套**：把「纯本地」文案改成「本地优先，可选云端同步」，并在清空进度页说明草稿不同步。

**为什么不做全量 field-level merge（报告 A03 原建议）**：要把 `wrong/fav/doubt/mastered` 从数组改成带时间戳的 map → **改变数据格式**，需要写迁移 + 改所有读写点，风险和工作量都远大于"并集"。并集能覆盖 90% 的实际丢失场景（丢失主要发生在"一侧标记被覆盖"）。

## 附录 · 「从后台抓出用户数据 → 重构 id → 改完塞回数据库」可行性核实

（2026-09-13 追加，探针实测，全量口径）

### 结论

**技术上行得通，但对你的数据几乎无用；而且只改数据库不生效。** 推荐改为「app 内一次性归一化」。

### 实测 1 · 用户数据里的 id 全是极光 UUID

| 项 | 数值 |
|---|---|
| 导出件 | 3 份 NDJSON，各 9 行 |
| 真实用户 | `lql`（state 396.4 KB / 3 科 / 15 会话 / 2,152 题位）、`lpc`（37.9 KB / 2 科 / 3 会话 / 290 题位）|
| 其余 7 行 | `flow_*` 空壳（state 仅 50 字节）；另有 1 个 `_init` 壳（`_id` 为 `$oid`）|
| 唯一 id 引用 | **3,104** |
| 形态 · 极光 UUID | **3,098** |
| 形态 · `ext-<hash>` | **0** |
| 形态 · 其他（nanoid）| 6 |
| 当前直接命中主 id | **3,088（99.48%）** |
| 走现有 aliasIds 命中 | 7 |
| 完全落空 | 9 |

站点 packs 构成：极光 **4,902 题（全 UUID）** + 扩展 **9,978 题（全 `ext-<hash>`）**。
→ **用户至今没刷过一道扩展题**，所以 A02 要保护的那 9,978 题在现有进度里贡献 0 条 id。

### 实测 2 · 落空 16 条逐个定性

| 类别 | 条数 | 能否救 | 说明 |
|---|---|---|---|
| 极光 UUID，merged2 有源 id | 10 | 部分 | 7 条属已上线 3 科（生物化学/生理学/医学免疫学）；3 条属「外基」——站点未上该科 |
| nanoid（`gmtb…`，16 位）| 6 | ❌ | merged2 全库（126,081 个源 id）无此 id，早期版本残留 |

真正值得救的只有 **7 条（0.23%）**。

另注：那 7 条「在 merged2 但不在当前 packs」的极光 UUID，正是**被合并吸收**的一类（同题多来源，极光那条没被选为主 id）—— 恰是 A02 建别名网后能自动找回的类型。

### 实测 3 · 只改数据库为什么不够

同步链路（`site/cloud/functions/quiz/index.js:99-104` + `site/sync.js`）：

1. `push` 是 **`set()` 全量覆盖**，一个用户一个文档（`_id` 为 32 位 hex 字符串）
2. `reconcile()` 按 `updatedAt` 比较，**谁新谁赢**
3. 本地浏览器里的旧 id 文档只要时间戳更新 → **会把改好的云端文档整包覆盖回去**

所以「改完塞回数据库」成立的前提是三条同时做到：

- 保留 `_id` / `uid` / `username`（否则导入 = 新建文档 → 用户数据分裂）
- `updatedAt` 调大到大于所有设备本地时间
- 同时清空或迁移**所有设备**的 localStorage

任何一条漏掉，手工改库都是白做。

### 推荐替代方案：app 内一次性归一化（约 30 行）

在学科 packs 载入、ALIAS 建好之后，对该学科 state 做一遍 `id → ALIAS[id] || id` 重写：

| 重写对象 | 形态 |
|---|---|
| `wrong` / `fav` / `doubt` / `mastered` | 数组，逐元素换 |
| `qstat` / `review` / `wrongReason` / `note` | map，换 key |
| `S.sessions[*].qids[*].id` | 数组内对象字段 |

性质：

- **幂等** —— 已是主 id 的不变
- **自动** —— 进入学科时顺带做，不做也能正常跑
- **多端一致** —— 数据自然变成主 id，下次同步自动推回云端
- **无需手工搬数据**

必要性来源：现在 `qstat` 用**主 id** 写（`app.js:571` `st.qstat[q.id]`），而 `wrong/fav/doubt/mastered` 里存的可能是**旧 id** → 当前就已存在「错题本能看到、掌握度统计读不到」的键错配。归一化顺手把这层也修了。

### 何时才真需要手工改库

- 想**彻底停用 aliasIds**（以后不再维护别名表）
- 要把某用户数据**迁移/合并到另一个账号**

### 一个前置风险

导出快照最新是 **2026-08-31**（`lql` 的 `updatedAt` = 1788147503785），而扩展题上线在其后。本地浏览器里的数据**很可能比这份快照新**，并且已经含 `ext-<hash>`。若仍要走手工改库，必须先拿到最新快照（站点内「导出备份」）。
